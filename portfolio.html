Agent Harness Abstraction Engineering

I build and compare agent harnesses to discover the layer between low-level agent primitives and human intent: abstractions that are precise enough for agents to implement and enforce, but legible enough for people to understand, inspect, and direct.

See the Systems Technical Discussion
The Engineering Question

How far can the abstraction boundary move upward?

Hooks, tools, scripts, skills, files, and model instructions are powerful primitives. They are also implementation-level concepts. Most professionals should not need to understand a PreToolUse hook or a shell script to decide how their agent should behave.

My work asks what stable concepts can sit above those primitives — jobs, phases, plugins, memory boundaries, authority gates, verification, consolidation — so the agent can translate conceptual intent downward into platform-specific machinery. The human engineers behavior at the level of meaning; the agent helps build the mechanism.

The research object is the abstraction layer, not one codebase. The published Seed architecture is one implementation family. Other private prototypes use many of the same conceptual abstractions with different enforcement mechanisms.

One System, Four Levels of Abstraction

Human Intent

Conceptual Control

"Verify before closure." "Keep this knowledge local." "Ask me before changing the substrate." "Separate observation from production." These are behavioral requirements a domain expert can reason about.

Behavioral Architecture

Modes, Memory, Authority

Explicit cognitive modes, long-horizon work, independent verification, consolidation, recovery paths, and controlled self-modification turn intent into an operating architecture.

Harness Abstractions

Jobs, Phases, Plugins

Reusable semantic units give the architecture names and boundaries: durable jobs, constrained phases, composable plugins, guards, state interfaces, permissions, and memory forms.

Platform Primitives

Hooks, Tools, Scripts, Skills

The implementation layer changes with the platform. Hooks intercept events. Scripts expose verbs. Tools act. Skills inject procedures. Files carry durable state and context.

Conceptual Invariants

Patterns I Keep Testing Across Harnesses

Work Becomes a Durable Object

A job outlives a chat turn. It carries objective, history, state, completion logic, and long-horizon memory so work can survive context boundaries and session boundaries.

Cognition Has Explicit Modes

Different kinds of work benefit from different action spaces. Observation, planning, production, verification, and consolidation can have different tools, write authority, evidence, and transition rules.

Behavior Is Composable

Small single-concern units compose into larger ceremonies. A plugin is a semantic boundary with an interface and owned state, not merely a folder containing scripts.

Soft and Hard Controls Stay Distinct

Some behavior should be coached; some should be mechanically enforced. I prefer to start soft, measure failure, and harden only where deterministic friction earns its cost.

Learning Has a Consolidation Step

Experience should not accumulate forever in working context. A deliberate consolidation process promotes durable knowledge, compresses transient state, updates behavior, and creates follow-up work.

Self-Modification Has Authority Boundaries

An agent can help modify the harness that controls it, but substrate changes should pass through explicit human authority, tests, evidence, and recovery or rollback paths.

Implementation Families

Same Questions, Different Mechanisms

I deliberately build more than one harness. If an idea only works because of one platform-specific trick, it is not yet a stable abstraction. Comparing implementations helps separate conceptual invariants from accidental mechanics.

Democratization

The User Should Learn the Architecture, Not the Shell Script

The adoption problem I care about is not solved by hiding agent complexity behind a nicer chat box. It is solved when the important concepts become understandable enough that a domain expert can make architectural decisions without implementing the underlying machinery.

Teach Semantics

A professional can learn what a job, phase, plugin, memory boundary, verification gate, or authority boundary means without learning Bash or the platform's hook schema.

Let the Agent Compile Intent

The user describes the behavior and constraints at the conceptual level. The agent translates that intent into the current platform's files, hooks, scripts, tests, skills, and configuration.

Keep the Result Inspectable

Abstraction should not mean opacity. The resulting harness remains local, inspectable, testable, and editable so the user can understand what became deterministic and why.

The long-term target is to reduce the default three-role relationship — agent, developer, user — toward agent and user. The developer does not disappear because complexity vanished. The developer role shrinks because enough of the complexity has been captured in a teachable substrate and a stable architectural vocabulary.

Research Method

Implementation Is How I Test the Abstractions

1. Form a Behavioral Hypothesis

Identify a recurring failure or capability gap: context drift, premature action, weak verification, unsafe self-editing, poor long-horizon continuity, or too much operator implementation burden.

2. Build a Mechanism

Implement a concrete answer using the primitives available on that platform. Instrument it, use it in real work, and watch where the design creates friction or fails.

3. Reimplement Elsewhere

Change the platform, enforcement strategy, team structure, or interface. If the concept remains useful while the mechanism changes, it is a stronger candidate for a stable abstraction.

4. Harden Only What Earns It

Keep judgment probabilistic where it should remain judgment. Add deterministic constraints only when observed failure makes their cost worthwhile.

Open Questions

What I Want to Test at Larger Scale

Abstraction Portability

Which harness concepts survive changes in model, CLI, tool system, organization, and workload — and which are artifacts of one implementation?

Harness as Evaluation Environment

Can a specific harness become an evaluation surface for model behavior: adherence to phase contracts, state transitions, authority, memory use, tool discipline, and recovery?

Model–Harness Co-Adaptation

How much of a harness should a model learn to operate natively, and which constraints should remain external and deterministic?

Agent-Generated Infrastructure

How much harness construction can be delegated back to the agent before the human loses meaningful understanding, ownership, or control?

Personal vs. Team Governance

How do shared context, authority, synchronization, review, and individual customization change when one harness coordinates multiple people and multiple agents?

Non-Technical Adoption

What is the smallest architectural vocabulary a professional needs in order to direct a capable agent to build and evolve a useful harness safely?

Current Research Constraint

Built Independently, Ready for Broader Evaluation

I have developed these systems independently using consumer-scale model subscriptions, local hardware, and real project work. That constraint has pushed me toward architecture that earns its compute and toward experiments I can inspect closely.

The next step is comparative evaluation at a larger scale: run the same semantic abstractions across models, harness substrates, workloads, and longer horizons; measure where they improve adherence and reliability; and identify which ideas deserve to become stable primitives rather than prototype-specific conventions.

Private Systems & Demonstrations

Much of the Implementation Is Private; the Behavior Is Demonstrable

Several of my more developed harnesses contain accumulated working context, team-specific architecture, or experimental substrate that I do not publish directly. For technical discussions I can demonstrate working systems, execution traces, architecture boundaries, failure and recovery behavior, tests, and the differences between implementations.

I am especially interested in discussing where my current abstractions fail. The purpose of multiple prototypes is to find the concepts that continue to make sense after the implementation underneath them changes.

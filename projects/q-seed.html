Project overview

Q-Seed is a second public route for the Seed architecture, built around an open Qwen Code framework. Like Seed Agent, it is meant to become a personal harness that carries durable memory, jobs, behavioral structure, and accumulated experience across model sessions. Q-Seed expands the ownership boundary by treating the CLI framework itself as part of the user's stack.

That deeper ownership creates a three-layer model. General runtime mechanisms can live in the Qwen Code fork; Seed-specific cognition stays visible in the .qwen/ brain; and each user's real work remains in the job and experience layer. The separation lets each capability find the layer that best matches its purpose and stability.

Q-Seed also provides a comparative path for the broader Seed architecture. As the Codex and Qwen versions mature, the same behavioral ideas can be expressed under different runtime constraints. Patterns that remain useful across both implementations become stronger candidates for stable harness abstractions.

Mission

Keep the framework and the cognitive harness independently evolvable.

Q-Seed treats framework, cognition, and job experience as distinct layers that can evolve at different speeds and under different authority.

A Seed-specific rule or working method lives in the cognitive layer where it stays easy to inspect and evolve. A general deterministic capability can live deeper in the framework when that produces a cleaner and more reusable primitive.

This creates a practical research environment for the Seed architecture: each layer can improve on its own cadence while the user retains ownership of the complete stack.

Why have both public Seeds?

Codex Seed and Q-Seed explore different ownership boundaries.

The projects share a common architectural lineage while testing it against different runtime conditions.

Working memory

Q-Seed is where the instruction / working-memory split became explicit.

This architectural cleanup is already influencing the Codex generation.

The original Claude Seed used CLAUDE.md both as durable local instruction and as mutable phase working memory. Q-Seed separated those responsibilities conceptually: QWEN.md for stable orientation and a candidate WM.md layer for dynamic local working memory.

The working-memory design also began specifying discovery, provenance, deduplication, refresh after edits, symlink safety, and predictable behavior during parallel tool calls. That work turns “memory in instruction files” into a more general harness concept that can be reused across runtimes.

Development roadmap

From open framework foundations to cross-runtime Seed comparison.

The roadmap develops the runtime boundary first, then uses implemented Seed behaviors to compare what belongs in the framework and what belongs in the cognitive harness.

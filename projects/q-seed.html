Project overview

Q-Seed is a second public route for the Seed architecture, built around an open Qwen Code framework. Like Seed Agent, it is meant to become a personal harness that carries durable memory, jobs, behavioral structure, and accumulated experience across model sessions. The difference is that Q-Seed also treats the CLI framework itself as part of the user-owned stack.

That deeper ownership creates a clean three-layer model. General runtime mechanisms can live in the Qwen Code fork; Seed-specific cognition stays visible in the .qwen/ brain; and each user's real work remains in the job and experience layer. The separation makes it possible to ask, capability by capability, which ideas belong to the general runtime and which belong to the cognitive harness.

Q-Seed is especially useful as a comparative project. As the Codex and Qwen versions mature, the same behavioral ideas can be expressed under different runtime constraints. What survives those differences is stronger evidence for a stable harness abstraction rather than a habit inherited from one implementation.

Mission

Keep the framework and the cognitive harness independently evolvable.

Q-Seed treats framework, cognition, and job experience as distinct layers that can evolve at different speeds and under different authority.

The project asks where a behavior truly belongs. A Seed-specific rule or working method stays in the cognitive layer where it is easy to inspect and evolve. A general deterministic capability can move deeper into the framework when that produces a cleaner and more reusable primitive.

This creates a practical research environment for the Seed architecture: one layer can improve without forcing every other layer to change with it, while the user still owns the full stack.

Why have both public Seeds?

Codex Seed and Q-Seed explore different ownership boundaries.

The projects share a common architectural lineage while testing it against different runtime conditions.

Working memory

Q-Seed is where the instruction / working-memory split became explicit.

This architectural cleanup is already influencing the Codex generation.

The original Claude Seed used CLAUDE.md both as durable local instruction and as mutable phase working memory. Q-Seed separated those responsibilities conceptually: QWEN.md for stable orientation and a candidate WM.md layer for dynamic local working memory.

The working-memory design also began specifying discovery, provenance, deduplication, refresh after edits, symlink safety, and predictable behavior during parallel tool calls. That work is useful beyond Qwen because it turns “memory in instruction files” into a more general harness concept.

Development roadmap

Open framework first, then comparative Seed behaviors.

The roadmap keeps the Qwen experiment coherent while the Codex Seed receives the current implementation focus.

Framework + cognition boundary

Stage 2

Runtime primitives

Implement the general mechanisms that belong in the Qwen fork, with separate review and compatibility evidence.

Stage 3

Cross-runtime comparison

Reimplement selected Seed behaviors and compare their shape against the Codex version to identify stronger harness abstractions.

New public implementation

Seed Agent / Codex

Each capability is restated as a behavioral objective, compared with Codex-native primitives, and implemented anew only if the behavior still earns a place in the new architecture.

What migrates: the reason a mechanism existed, the failure mode it addressed, the useful abstraction, and the evidence around it. What does not automatically migrate: Bash code, .claude/, CLAUDE.md footers, exact plugin names, thresholds, file layouts, and Claude-specific workarounds.
A deliberate difference from Q-Seed

Seed Agent does not begin by modifying Codex itself.

Codex is treated as the runtime. The first engineering target is the user-owned cognition around it, not a custom Codex fork.

Use native Codex primitives first

Before recreating a historical hook or workaround, inspect what Codex already supplies through its instructions, tools, skills, scripts, sandbox, and other supported extension surfaces.

Keep Seed meaning outside the runtime

Jobs, cognitive phases, plugin contracts, memory behavior, authority rules, verification, and learned working methods should remain visible and editable as harness cognition whenever they can be guaranteed there honestly.

Do not invent a fork without evidence

If a future capability truly requires a lower-level primitive Codex does not expose, that becomes a separate architectural decision. It is not the starting assumption of this project.

One lesson already carried forward

Instructions and working memory should not be the same file merely because the runtime can load it.

The private Claude Seed used directory-local CLAUDE.md files for both stable instructions and the mutable working surface used by its phases. The Codex version starts by separating those roles conceptually.

AGENTS.md

Stable, scoped instruction. It should carry durable rules and local operating boundaries rather than inflate and deflate with every work cycle.

WM.md — candidate name

A future dynamic local working-memory organ. The name is provisional; its grammar, discovery, refresh, authority, persistence, concurrency, and phase interaction are intentionally not frozen yet.

Structured state stays structured

Plugin and job state should have clear owners and interfaces rather than being hidden inside prose merely because prose is easy for the model to read.

PR-by-PR development

One bounded behavior at a time.

The project is intentionally not starting with a dozen empty plugin directories. The next real capability should earn its anatomy through evidence.

Study the reference behavior

Read the frozen implementation, its tests, its history, and the user rulings that shaped it. Identify the problem rather than memorizing the files.

Write the objective in platform-independent language

What must the Seed reliably do? What is explicitly outside this capability?

Inspect Codex-native surfaces

Determine which guarantees Codex already provides and which still need external harness machinery.

Define ownership and recovery

Name state owners, interfaces, authority, dependencies, failure modes, and escape paths for any hard invariant.

Specify acceptance evidence

Tests should describe the behavior that matters rather than simply reproduce the old implementation shape.

Implement the smallest vertical slice

Build enough to exercise the behavior end-to-end, learn from real operation, and only then generalize.

A Seed people can actually clone

The public repository is the generic cognition layer, not one person's life.

The eventual goal is a mature base a user can clone and continue cultivating. That does not mean Hadosh Academy's own jobs, history, and private operating context belong in the public distribution.

Public Seed

Reusable cognition: job semantics, plugin behaviors, memory structures, phase systems, verification, authority, and the mechanisms needed for the Seed to keep evolving.

User layer

The user's actual jobs, plans, personal preferences, domain context, artifacts, outcomes, and accumulated experience remain local to that deployment.

Two onboarding paths

Some users can clone a mature Seed and learn it. Direct client work can instead begin from a thinner harness so the user learns the architecture while participating in its construction.

Current state

The foundation is real. The cognitive system is not built yet.

The repository has been reset so future work no longer inherits the abandoned Claude release shell. It is intentionally sparse and not ready for installation or general use.

What exists now is the clean identity and architectural boundary: Codex as the runtime, .codex/ as the starting cognition surface, the distinction between instructions and future working memory, and the rule that historical mechanisms are evidence rather than specifications.

The next meaningful milestone is not “fill the old plugin list.” It is to choose one behavior from the frozen reference, understand it deeply, and produce the first Codex-native implementation with tests.

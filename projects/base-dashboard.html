Project overview

Base Dashboard removes the work every user should not have to pay an agent to recreate: a cross-platform local web surface, an interactive agent connection, persistent feedback, recovery, and a review boundary. It does not pre-decide the user's profession, pages, objects, vocabulary, or workflows.

A person normally reaches this substrate during Phases 6–7 of Start Here, after an existing agent has learned enough about them to propose the first useful pages. Codex users can adopt the implementation directly once its public release gate is complete. Other CLI agents can use the documented behavior as a porting contract rather than pretending that changing one executable name creates a compatible harness.

The repository is being prepared for public release under the Base Dashboard name. The website will link it only after its public identifiers and launch commands match that name.

Implemented foundation

Empty page. Complete first relationship.

The canvas is sparse by design; the user-agent loop is not.

Visible surface

An empty responsive canvas, a lower-left Wiki control, a lower-right Feedback control, feedback threads, attention states, and future-route context.

One interactive session

A strict launcher checks Git, Node.js, tmux, Codex CLI, authentication, and WSL2 on Windows, then opens the dashboard and attaches one repository-scoped foreground Codex session.

Durable responsibility

Feedback is saved before wake delivery. Raw input, route, messages, interpretation, verification, review, and reopening history remain locally inspectable and recoverable.

Compartmentalized anatomy

Two cognitive concerns. One transport boundary.

Each part owns a narrow objective instead of accumulating one giant feedback script.

Contextual feedback

Owns thread policy, raw input, page context, lifecycle operations, agent questions, verification, user review, event voices, schemas, commands, documentation, and tests.

Agent stop state

Owns the clone-local idle, active, waiting, and paused modes. Runnable work blocks Stop; legitimate waiting is allowed only when no other runnable feedback remains.

Dashboard runtime

Owns the server, tmux session, prompt delivery, delivery evidence, outbox, startup recovery, and browser launch. It transports events; it does not own feedback cognition.

The implemented lifecycle

Feedback is saved first. Attention follows.

The dashboard never relies on a transient prompt as the only copy of the user's intent.

1. Persist

The user comments from a route. The system records the raw words and context, assigns a stable ID, and only then creates a bounded wake event.

2. Wake or queue

If Codex is idle, tmux submits an orienting voice to the same foreground session. If Codex is busy or paused, the event stays queued without interrupting the active tool call.

3. Work or ask

The agent reads authoritative state by ID, interprets the request, starts bounded work, or asks a question in the same thread. Waiting becomes legitimate only when no other feedback can progress.

4. Verify and return

The agent records what changed and how it was checked, then marks the thread ready_for_review. Only the dashboard user can accept, dismiss, or reopen it.

Honest maturity

What 1.0 does not claim.

The release separates demonstrated machinery from the curriculum for later growth.

Base Dashboard 1.0 is single-user and loopback-only. It does not ship accounts, remote access, cloud synchronization, team roles, a general job plugin, or a full OPEVC engine. Feedback records are the first durable work queue; they may later create or enrich jobs, but they are not quietly renamed into a job system today.

Automated tests cover lifecycle, schemas, hooks, tmux command construction, outbox behavior, APIs, interface behavior, accessibility, build, and smoke paths. A real authenticated Codex session, browser opening, tmux attachment, and operating-system integration remain a separate local acceptance procedure. Deterministic evidence does not impersonate live acceptance.

Differentiation

Every clone should become less generic through use.

The common substrate removes repeated setup; the user's context decides what grows on top.

After Start Here establishes an Asset Charter and a verified web-to-CLI handoff, the helping agent proposes the smallest useful pages in the user's own terminology. Real feedback then reveals which objects deserve durable state, which repeated responsibilities deserve plugins, and which multi-cycle work deserves explicit jobs or OPEVC phases.

Later Base Dashboard versions may add proven capabilities, but version numbers do not replace local evolution. A research environment, client practice, family world, and project portfolio should not inherit the same nouns, permissions, or completion tests merely because they share a starting substrate.

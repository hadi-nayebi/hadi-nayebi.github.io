Team Harnesses

A team harness gives a small startup or project group one shared cognitive substrate without forcing everyone into one central chatbot. Each member can use their own local CLI agent, while the private repository, dashboard, shared context, jobs, plugins, and governance belong to the team.

Mission

Turn the team's working methods into shared, inspectable cognition.

The system should help a small team coordinate work and agent behavior without erasing individual working styles.

The shared harness holds the team-level layer: common project context, jobs, repeatable methods, plugins, authority, and the rules that should be consistent no matter which member's agent is working. Member-local context and personal preferences can remain local.

The result is closer to a shared digital office than a shared chat thread. The repository is concrete, versioned, and inspectable; the dashboard makes it usable beyond the terminal; each member's CLI agent can animate the same substrate independently.

One shared office, many agents

The repository is the common substrate—not one central model session.

Every member can clone the same private repository and operate against the same team-owned harness.

Shared team layer

  • Harness behavior and plugin contracts
  • Project context, milestones, methods, and decisions
  • Shared jobs and workflow state
  • Dashboard views and governed interactions
  • Authority for changing the shared substrate

Member-local layer

  • Temporary working context
  • Personal notes and preferences
  • Compatible CLI/model choice
  • Member-specific branches or experiments
  • Personal customization that does not redefine team policy
Shared interaction surface

The dashboard turns the harness into a team workspace.

Group systems need a common browser surface because not every member should have to operate through a terminal.

Jobs

Start, inspect, and review shared work across members and agent sessions.

Questions & approvals

Surface places where the harness needs human judgment, review, or authority.

Workflows & feedback

Expose milestones, comments, processes, and team feedback while CLI agents operate the underlying repository.

The dashboard and CLI are two surfaces over the same substrate. A dashboard action can create a job, capture feedback, or trigger work without creating a second disconnected system.
The harness teaches its own extension patterns

Existing plugins become examples for the next plugin.

The goal is a team that can continue cultivating its own system after the initial build and training.

1. Need

The team identifies a repeated behavior, coordination problem, or control that deserves a stable owner.

2. Local examples

A member points their CLI agent at mature plugins and context already inside this harness.

3. Consistent extension

The agent follows the local anatomy, interfaces, state rules, tests, and terminology the team has learned.

4. Governed promotion

The new behavior enters the shared substrate through the team's review path.

Development roadmap

From initial shared substrate to a team that can extend its own harness.

The applied prototype already established the core team topology and several mature plugin patterns; the next stages deepen that operating model.

Stage 0 · Team foundation

Shared repo + dashboard

Establish the common repository, local agent model, shared dashboard, and team-level authority boundary.

Stage 1 · Current

Stable plugin patterns

Clean and mature a small number of foundational plugins that teach the local anatomy and governance model.

Stage 2

Team-led extension

Members use their own agents and the existing harness as context to add new team-specific behaviors consistently.

Stage 3

Operational cortex

The harness coordinates more of the team's research, workflows, decisions, and accumulated working knowledge while remaining user-governed.

Team Harnesses

For roughly 2–7 people working on the same startup or project. The team shares one private-repository harness and a common dashboard, while each member can still use their own local CLI agent to animate that shared cognition.

One shared office, many agents

The repository is the common substrate—not one central chat session.

Every member can clone the same private repository. Their local CLI agents operate against the same team-owned harness and shared project context.

Member A can start work with one model while Member B uses another compatible CLI agent elsewhere. The shared harness is what keeps team-level behavior, project context, jobs, and authority concrete across those sessions.

The goal is coordinated cognition without requiring the team to share one giant conversation or one identical personal agent.

The group needs a shared surface

The dashboard is the team's common interface to the harness.

This is where group harnesses differ most visibly from the individual Seed. A team cannot reasonably expect every interaction to happen through a terminal.

Jobs

Start, inspect, and review shared work without hunting through individual agent sessions.

Questions & approvals

Make human judgment visible when the harness needs a team member to decide something.

Workflows & feedback

Expose processes, milestones, comments, and review in a browser while CLI agents operate the underlying repository.

The dashboard is not a second system. It reads and writes the same repository that the agents use, so dashboard actions and CLI work remain part of one shared substrate.
Shared does not mean everything

Team cognition and personal working context need different homes.

The architecture should make it clear when an agent is acting for one member and when it is changing something the whole team depends on.

Shared team layer

  • Harness behavior and plugin contracts
  • Project context, milestones, methods, and decisions
  • Shared jobs and workflow state
  • Dashboard views and governed interactions
  • Authority for changing the shared substrate

Member-local layer

  • Temporary working context
  • Personal notes and preferences
  • Compatible CLI/model choice
  • Member-specific branches or experiments
  • Personal customization that does not redefine team policy
The harness becomes its own teaching material

New plugins should learn from this team's existing plugins.

The long-term goal is that the team can extend the harness without always needing the person who initialized it.

1. Need

The team identifies a repeated behavior or coordination problem that deserves a stable owner.

2. Local examples

A member points their CLI agent at the mature plugins and context already inside this harness.

3. Consistent extension

The agent follows the anatomy, interfaces, state rules, tests, and terminology that this team has already learned.

4. Governed promotion

The new behavior enters the shared harness through the team's review path rather than silently changing everyone else's agents.

Team ownership needs authority boundaries

Editing project content is not the same as editing the machinery that controls future behavior.

The shared substrate should be easy to use and harder to change accidentally.

Ordinary work

Research, notes, artifacts, and team content can follow the collaboration model appropriate to the project.

Harness changes

Plugins, authority rules, shared cognition, and other substrate changes can require PR review or explicit approval.

Roles

Not every member needs permission to rewrite the shared harness just because every member uses it.

Why build this from scratch?

The construction process is part of the training.

The team should leave the initial engagement understanding its own harness well enough to continue evolving it.

Instead of dropping a mature personal Seed into a startup and asking everyone to learn a dozen unfamiliar concepts at once, the first stable behaviors, dashboard surfaces, jobs, and governance rules are built with the team involved. Earlier harnesses are pattern libraries, not mandatory code packages.

That makes the terminology and architecture local enough that team members can later say “check how our existing plugins do this” and have their own CLI agent extend the harness consistently.

Team Harnesses

A team harness is not one chatbot shared by everyone, and it is not several unrelated personal agents. It is a team-owned cognitive substrate that multiple local CLI agents can animate independently while remaining aligned to the same shared context, rules, interfaces, and governance.

One office, many agents

The repository is the shared office. Each person brings their own agent into it.

Every member clones the same private repository. The harness and dashboard live with the project files, so the shared cognition is concrete, versioned, inspectable, and available to each member's local CLI agent.

A member can work directly in the terminal, or use the dashboard as the simpler interaction surface. The important point is that both surfaces operate on the same repository rather than creating two disconnected systems.

This lets the team share a stable cognitive substrate without forcing everyone to share one model session. Member A can start a job with their own agent while Member B is working elsewhere; both agents read the same team-level context and operate under the same harness contracts.

Compartmentalize team cognition

Some cognition belongs to the team. Some should remain individual.

The system works only if “shared” does not become a synonym for “everything.” Team-level policy, project state, and common methods need a home; individual working context and personal agent preferences can remain local.

Shared by the team

  • Team-level harness behavior and plugin contracts
  • Shared project context, milestones, methods, and decisions
  • Common dashboard views and interaction surfaces
  • Reusable job semantics and governed workflows
  • Authority rules for changing the shared substrate

Can remain individual

  • Each member's CLI/model choice where compatible
  • Temporary local working context
  • Personal preferences and private notes
  • Member-specific branches or experimental changes
  • Individual agent customization that does not redefine team policy
The design goal is not perfect uniformity. It is a clear contract for when an agent is acting as my agent inside the team versus when it is acting on a shared team object that other people and agents depend on.
A second interaction surface

The dashboard makes the shared harness usable without making the terminal the team's entire office.

The local browser dashboard reads from and writes to the same repository. It is especially useful for people who should understand the concepts without living in a CLI.

Jobs and work state

See active work, start or review jobs, inspect progress, and keep long-running work visible outside one agent session.

Questions and approvals

Surface places where the harness needs human judgment rather than burying decisions inside terminal transcripts.

Workflows and feedback

Expose team-level processes, comments, review, and feedback in a form ordinary members can use while the CLI agents operate the underlying harness.

The dashboard does not replace the harness. It is a view and control surface over the same local substrate. A dashboard action can create a job, capture feedback, or wake an agent; a technical member can still work directly in the terminal when that is more efficient.

The harness teaches its own patterns

Existing plugins become local examples for the next plugin.

A mature team should not need the original architect every time a new behavior is required. The repository itself should become enough context for a member and their CLI agent to extend it consistently.

1. A need appears

The team identifies a repeated behavior, coordination problem, or control that deserves a stable owner.

2. Inspect local examples

The member points their CLI agent at the existing mature plugins and the harness's own context.

3. Build in the local anatomy

The agent learns how this particular harness organizes state, interfaces, hooks, tests, and authority rather than importing a universal template blindly.

4. Review and promote

The new behavior enters the shared substrate only through the team's governed change path.

This is one reason the team implementation is built from scratch rather than simply handing the group the full personal Claude Seed. The team learns its own vocabulary and architecture while the first stable behaviors are being created.
Shared cognition needs authority

Changing a project file and changing the machinery that controls everyone's agents are different acts.

A small team can move quickly without making the harness itself casual.

Ordinary work stays fluid

Research, project content, notes, and other team work can follow the normal collaboration model appropriate to the project.

Harness changes get stronger review

Plugins, authority rules, shared cognition, or other substrate changes can require a pull request or explicit approval before they affect every member's agent.

Roles can differ

Not every member needs permission to rewrite the shared harness. Ordinary members can use and extend the system through governed paths while maintainers protect the stable layer.

Why cultivate instead of install

The training is partly the construction process.

For a direct team engagement, the objective is not only to deliver software. It is to leave the team able to understand and continue evolving its own harness after the initial training ends.

The first plugins, shared concepts, dashboard surfaces, and governance rules are built with the team in view. Members learn what a plugin means in their harness, how jobs behave, what is shared, which changes require stronger authority, and how to point their own agents at existing patterns when they want to add something new.

This approach produces more implementation diversity than copying one universal Seed into every company. That diversity is useful: it reveals which abstractions remain stable across personal and team systems and which were merely habits of one prototype.

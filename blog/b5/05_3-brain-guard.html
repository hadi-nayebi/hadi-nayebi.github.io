Context Window Discipline — brain_guard

May 14, 2026 • revised September 10, 2026 • 15 min
Tier 2 Architecture Seed Agent Plugins Always-On
By Hadi Nayebi & Claude Opus 4.8

Essay 5.3 — The Always-On Digital Cortex, Part 3 of 9.

Essay 5.2 covered the floor — the test gate that makes every plugin code change conditional. This part covers the ceiling: the always-on plugin that owns the seed agent’s relationship to the model’s context window.

What it owns

brain_guard is the always-on plugin that owns the compaction discipline: an inspectable, job-scoped handoff file plus a deliberate seal, clear, and reorientation boundary. Claude Code already provides manual /compact and native auto-compaction; its current documentation says auto-compaction normally starts around 95% of the usable context window. This prototype adds an earlier, operator-configured discipline around that native behavior. Its hooks measure the current context, coach the agent to externalize what matters, and progressively narrow file tools before the session reaches the provider’s late emergency boundary. Outside a gmode maintenance side quest, the prototype’s normal path seals its own file and invokes /clear; native /compact remains available only inside gmode. That distinction matters: brain_guard does not claim Claude Code lacks compaction. It makes the carry inspectable and recoverable before clearing the chat. ⓘ

The compaction file — the thing that survives the clear

Compacting a conversation is destructive. The chat shrinks, and whatever was only in the chat is gone. So the first question brain_guard answers is not when to compact but what must survive the compaction — and the answer is a file.

For each job, brain_guard maintains a compaction chain: one working file per job, run, and sequence. It carries the cognition about a job, separate from the work itself. The work lives where it always lived — in the CLAUDE.md hierarchy, Git, plans, and other durable files. The compaction file holds the other thing: how the work is going. Open threads. Assumptions the agent is leaning on. Loops it got stuck in. Fallacies and blind spots it should not repeat. Plus, in a rolling Prior Summary, the top-level facts and principles the next session needs to resume thinking, not just to re-read state. When a sequence seals, the old file remains as a frozen, readable record and a new sequence begins with a compact index back to that record. ⓘ

The deeper purpose is sharper than survival. The file forces the seed agent to spend compute not only doing the job but optimizing how it does the job. At each phase’s exit, the agent reviews how its own instructing layer — the coaching voices, the per-job injections — actually steered the work. If a voice injection sent the work down a wrong path, that finding lands in the compaction file, where a later run can read it and re-tune the injection. The file is a node in the seed agent’s self-improvement loop for its own instructions. How each phase actually compels that reflection before it can advance is the phase layer’s job — the Essay 6 series covers the per-phase reflection gate. ⓘ

It is built gradually, then deliberately condensed at the sequence boundary. The working file is born from a template and grows as phase work adds new reflections to its sections. CONDENSE does not metabolize this file with ordinary managed-file cleanup, but the seal is allowed to deduplicate, fold, organize, and shrink it. That is not a contradiction. The live file preserves inspectable cognition while the job runs; the seal reduces its carrying cost before it crosses into the next sequence. The frozen prior file and its back-reference preserve the recovery path when the rolling summary leaves out detail. ⓘ

Two distinct events touch the file, and they should not be confused. A phase-exit append is the frequent one: every phase, on its way out, writes its slice into the file. A full compaction event is the rare one, threshold-triggered — when a context ramp or a file-size ramp hits its ceiling, the tools progressively block, the finalization pass seals the file, and the session clears and re-injects. The append happens at every phase boundary; the compaction event can fire mid-phase, the moment a ramp tops out, not only at a phase exit.

How it works — the progressive squeeze

A pre-call sensor reads the running token count, and the context ramp acts on current total context as a percentage of a configured window — no session baseline and no subtraction. The checked-in prototype is presently running an experimental 31% / 39% / 42% override: coaching begins at 31%; at 39%, Read is blocked while Edit, Write, and Bash remain available; at 42%, Edit, Write, and MultiEdit join the block list, with the job’s own compaction file carved out. The older 20% / 25% / 30% values remain documented defaults, not the live configuration. Bash is never blocked at any stage: the agent still needs a path to inspect state, seal the file, and invoke the clear boundary. ⓘ

Running beside it is a heartbeat, and the heartbeat deliberately uses a different measure. It counts context accrued since this session’s baseline in 10,000-token windows. The hard floor asks for two metacog-reflect executions per window; the coach recommends three; and a cap of eight required executions prevents the debt from becoming an unwinnable treadmill. The context ramp asks, “How full is the whole window?” The heartbeat asks, “Has this session spent enough attention recording what it has learned?” Keeping those questions separate lets cognition accrue ahead of the boundary instead of being reconstructed under pressure. ⓘ

The stage positions are tunable; the architectural fact is the progressive tightening. Rather than letting the agent drift toward a late wall, brain_guard removes access in stages until the graceful move is to seal-and-clear. The tightening is graduated, not a single lock: the first hard band cuts off new reading while leaving the tools needed to finish and commit; the critical band narrows further; Bash, the focused compaction-file carve-out, and deliberate operator recovery remain reachable. The discipline creates pressure without designing a dead end. ⓘ

There is a second ramp running alongside the first, and it watches a different gauge. The context ramp watches the model’s window. The file-size ramp watches only the authored work sections of the compaction file — because the cognition can outgrow its own home long before the context fills. With the current θ_lc target of about 2,000 words, 70% starts coaching, 80% adds a nonblocking trim warning, 85% blocks further growth, and 100% is the absolute ceiling. The Prior Summary has its own 30%-of-θ_lc budget and is excluded from the work-section count, so a required historical carry cannot itself wedge the seal. The two ramps share graduated pressure, but they measure different things and do not need identical percentages. ⓘ

Whichever ramp reaches its ceiling first demands the same response — but the ceiling does not fire compaction on its own. It narrows the path to the focused file and its boundary operations: the agent can polish the compaction file, bring its Prior Summary current, and issue the self-compact command. New agent dispatch is blocked, because a returning subagent would re-inflate context and defeat the seal. The session holds there until the agent supplies the cognition the script cannot invent, passes the seal, and clears the conversation. If neither tmux nor X11 dispatch is available, the seal still persists and the chain still advances, but the session honestly remains uncleared until the operator invokes the boundary manually. ⓘ

Shape compels production

The compaction file is shape-enforced. It carries a fixed set of sections — Forward State, Open Threads, Assumptions & Risks, Process Insight, and a rolling Prior Summary — and each phase-exit note is routed into the section it belongs in. Scope boundaries and binding user directives go to Forward State. Uncovered sources, deviations, and gotchas go to Open Threads. What verification might have missed goes to Assumptions & Risks. Why-this-over-that and cycle lessons go to Process Insight. The titles are not decoration — each names a specific kind of thinking (the next move, the open unknowns, the load-bearing assumptions and what would break them, the lesson learned), so an agent writing under them is prompted for real cognition rather than filler; and the instructions add one standing rule — every entry must contribute something new, never a repeat of a prior reflection or another section — so the chain compounds instead of bloating, all without a content-policing gate. Beside those five authored sections sit two more the agent handles differently. Git Commit Messages it never writes by hand — every phase commit’s message is appended automatically, giving the next session a ground-truth trail of what changed without re-reading the full diff. And Settled Decisions is an append-only, size-exempt ledger: when the agent settles something — where a thing belongs, a diagnosed root cause — it records the decision here so a later session resumes from it instead of re-deriving, or worse reversing, a call it already made. Seven sections in all, and the names and their order are the same in every phase. What flavors by phase is the prompt each working section asks for: an OBSERVE file is asked for what was already surveyed and what is still uncovered, so the next session does not re-observe ground already walked. The shape stays fixed; only the questions sharpen to the work at hand. ⓘ

The sections aren’t gospel. The shape is.

Call this shape compels production: a compartment that demands a structured shape forces the agent to attempt the thinking each section calls for, and the resulting content becomes useful context. The agent cannot stack every thought in the easy section and silently skip the hard one because the seal requires the five authored sections to be nonempty. Shape makes omissions visible and raises the cost of shallow reflection. It does not prove that the content is insightful, correct, or complete; those remain reasoning and verification problems. ⓘ

The pattern is portable. Structured git commits, structured plan files, structured subagent dispatches — every time a shape demands content, the content rewards the next step. A consultant could use the same trick on weekly client briefs — a fixed five-section template (scope, open questions, decisions taken, evidence, next checkpoint) forces the substantive thinking the prose would otherwise skip. The same trick lands in interaction_summary (Essay 5.5). ⓘ

Clear and inject

When a ramp hits its ceiling, brain_guard runs a finalization pass — an ordered, inspectable sequence that seals the current compaction file — and then clears the session. The fresh session’s SessionStart(source=clear) hook reloads the focused chain and its orientation from disk; a verified follow-up starts the first post-clear turn. The whole design is built for transparency: the finalization pass, the frozen prior file, the new working file, and the Prior Summary are all inspectable. The rolling summary is deliberately authored before the clear rather than generated invisibly at the boundary. ⓘ

The finalization pass is a quality gate, not a ghostwriter — it invents no missing cognition. Its structure and gates are phase-independent: it checks the same seven sections and never substitutes for the phase’s separate reflection gate. Two outputs are phase-aware without changing what gets sealed. An empty work section receives a populate prompt shaped for the phase in which the file was worked; at an advance boundary, --shape names the destination phase so the wake frames the next session for where it is going. The pass deduplicates and folds redundant entries, checks that all five authored sections contain something, enforces the separate Prior Summary budget, stamps provenance, freezes the current sequence, and rolls a fresh one. It aims to put the work sections at or below the 80% seal margin. A result above that target can still pass only while it remains below the 85% block band; at or above the block band the seal fails, preventing a fresh read-only session from being born already wedged. ⓘ

The boundary rides a hacky-but-honest carrier: clipboard-and-keystroke input under X11, or terminal-multiplexer paste primitives under tmux, picked by one selector. Both paths escape first, verify that the prompt is ready, submit /clear, verify that the clear executed, and only then deliver a follow-up to the fresh session. The sealed cognition itself reloads from disk through the session-start hook; it is not pasted wholesale through the terminal. If Claude Code ships a native API for an agent to manage this boundary, the terminal-typing layer can retire without discarding the file, seal, and recovery discipline. ⓘ

There is one more move, and it leans on the whole point of the seed agent: the mind lives on disk. After the clear, the conversation has shrunk to nothing, but the focused job, the current phase, and the working memory all survived — they were never in the chat to begin with, and now the sealed compaction file rides in alongside them. So the moment the fresh session is born, the digital cortex re-grounds itself: it resets its context-fill tracking, reads the focused job and the live phase straight off disk, and re-presents the same phase-entry coaching the agent heard when it first entered that phase. Because the re-grounding hangs on the /clear session boundary, the reset is direct and deterministic — a fresh session is unambiguously fresh, so the context-fill tracking resets cleanly with no waiting and no guesswork. A clean boundary is self-announcing: the digital cortex knows the exact instant it is born and re-grounds on the spot, with no grace window to wait out and no detector watching for a boundary it has to infer. The keystroke follow-up still kicks off the first turn; a reflex that fires on session birth can hand the agent its bearings, but it cannot make the agent start talking. That division is deliberate: the re-grounding is automatic and certain, so even if the follow-up keystroke mis-fires, the fresh session already carries its own orientation. ⓘ

The ceiling is not the only thing that triggers a clear-and-inject. Two other moments fire the same boundary. The first is job completion: when the seed agent finishes a job, a required seal runs before the job can close — the same finalization pass wraps the finished job’s cognition into its directory, then the boundary clears and injects only a transition note, the sealed Prior Summary, never the full old file and never a fresh template. The next job is not focused yet, so there is nothing to start fresh; the job that defines a compaction file is the one that creates it, at its own focus. A job never ends with an unsealed compaction file — the advance that closes it checks for the seal stamp before it fires. ⓘ

The second is focus itself. Picking up a job from idle is a clear-and-inject too: focusing a job whose compaction file already exists — a return after a pause, a reactivated run — clears the session and injects that file, the reload path; focusing a job with no file yet creates it from the template and injects that, a clean cognitive start that sheds the prior job’s residue. Two edges are deliberately carved out. A prompt that bootstraps a job — a user prompt that creates a fresh focused job — does not clear, because the user’s live prompt thread is already the job’s opening cognition and there is no stale residue to shed. And pausing a job does not seal: the live file stays with the job, and the metacognition written since the last phase exit is the bounded loss of a mid-phase pause — the work itself is safe on disk in the CLAUDE.md layer. ⓘ

And because each new sequence opens with one bounded rolling Prior Summary, the chain can grow without injecting every historical file into every session. The active file describes current cognition; the Prior Summary folds older lessons into an index and keeps back-references to the frozen files. Session thirty can recover what session two recorded by following that index without carrying all thirty files by default. The fixed-cost claim applies to what is loaded routinely, not to perfect recall: the rolling summary is lossy, and exact detail survives through the on-disk back-references. ⓘ

What would break without it

Without brain_guard, Claude Code would still compact a long conversation. What disappears is the prototype’s earlier, job-scoped discipline around that event: a reviewable record of open threads, assumptions, failed loops, settled decisions, and instruction-level lessons; an enforced moment to author that record; and an indexed path back to exact prior files. Native compaction creates a structured summary and reloads durable instructions, so it is more capable than “keeping scraps.” The additional risk is that a provider-generated summary optimizes for general conversational continuity, while this seed needs a specific job’s cognitive and procedural state in a shape the operator can inspect before crossing the boundary. ⓘ

What you would customize

brain_guard is the plugin most architects tune the moment they adopt the seed. Almost every knob has a defensible reason to move.

You would tune the context percentages for your model and workload. The checked-in 31% / 39% / 42% values are an experiment, while 20% / 25% / 30% remain the documented defaults. Both are fractions of MAX_CONTEXT_TOKENS, measured on current total context. Percentages rescale only when that denominator is correct: the prototype assumes one million tokens and deliberately requires CONTEXT_WINDOW_ACK=1 when an operator configures another real window. Claude Code currently distinguishes standard 200K sessions from eligible extended 1M sessions, so the operator must set the actual window rather than infer it from a model family name. What you tune is where in this workload quality and recoverability begin to soften, then validate the thresholds with observed sessions. ⓘ

You would customize the compaction file’s sections. The five authored sections name what this prototype values — Forward State, Open Threads, Assumptions & Risks, Process Insight, Prior Summary — with two more the machinery manages for you: an auto-fed Git Commit Messages trail and an append-only Settled Decisions ledger, seven in all. Your seed may need different sections for your kind of work: a legal-research seed may want a "citation-state" section; a project-management seed may want a "decision-log" section. And there is a finer knob beneath the names — the prompt each section asks for can flavor by phase, so an OBSERVE session and an EXECUTE session are steered to record different things under the very same headers. The names aren’t gospel, and neither are the prompts. The shape is. ⓘ

You would tune θ_lc, the compaction file’s work-section target size, and the ramp positions that key off it. Two thousand words is this prototype’s ceiling for the counted work sections; the Prior Summary and Settled Decisions have separate treatment. A seed running denser, longer jobs may want more headroom, and a seed running short, hot cycles may want less. You tune the 70% coach, 80% warning, 85% block, 80% seal target, and 100% ceiling together so the file has useful runway before it becomes a recovery problem. ⓘ

You would tune the metacognition requirement — how many reflection steps each phase must run before it can move on. More steps means more compute spent optimizing how the work is done; fewer means more compute spent on the work itself. That dial is how an operator decides how hard their seed thinks about its own thinking. ⓘ

You would choose your dispatch mechanism. The current prototype ships two paths — X11 keyboard injection and tmux paste-buffer — and the same carrier delivers the clear-and-inject payload. Your environment may need a third (an SSH-bridge variant, a Windows Terminal handler). If Claude Code ships a native API for an agent to manage its own session boundary, you drop the keyboard-injection layer entirely without touching the rest of the plugin. ⓘ

You would add or split stages. Three stages is the current shape; nothing in the architecture forbids four or five. A high-stakes seed may want an extra stage between the Read block and the critical block that pulls MultiEdit early, before the rest of the write tools. A seed working in shorter, hotter cycles may collapse the soft stage and block Read at a lower percentage of its configured window. What no stage touches is Bash — the seed needs it to inspect and seal durable state and invoke the clear boundary, so leaving Bash open is a recovery invariant, not a stage position. ⓘ

What you would not do is remove the progressive-tightening principle. Letting the agent drift toward the provider’s late automatic boundary, then discovering at the worst moment that its job-specific cognition was never made durable, is exactly the failure mode brain_guard was built to prevent.

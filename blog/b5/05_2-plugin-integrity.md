# Plugin Edit Safety — `plugin_integrity`

## What it owns

`plugin_integrity` exists to keep accidental edits from regressing a plugin's established logic. It combines a named edit scope, a Git checkpoint, the plugin's shell tests, and an explicit close-out. Before code work begins, the reference architecture requires a shaped `[PLUGIN-LOCK]` request naming one plugin, the specific changes, the reason, and the tests to run. The request is admitted only in one of two protected contexts: the operator's deliberate gmode lane or a focused job for which the user already approved plugin work. Creating a new plugin uses the same admission boundary as editing an existing one. *[ref: plugin-lock-admission-boundary | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

Once admitted, the lock applies to the plugin's logical and executable surfaces: hooks, scripts, configuration, hidden state, and existing shell tests. Narrative and coaching surfaces — the plugin's `CLAUDE.md`, Markdown under `docs/`, `voice.xml`, and Markdown agent definitions — do not require a plugin lock. Shared utilities under `plugins/lib/` also sit outside any one plugin's lock. “Lock-free” here means free of the plugin-edit ceremony; the current phase's scope and write rules still apply. The distinction lets CONDENSE update learning and history without pretending that prose and executable enforcement carry identical risk. *[ref: protected-and-exempt-plugin-surfaces | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

The phase-independent role to keep in mind is the **test boundary**: an admitted change opens one plugin, and leaving that protected scope requires closing or defending the lock. The guard watches relevant Claude Code tool calls and transition commands rather than every action in the session. Subagents skip automatic close-out but still respect lock scope, hidden-state, test-file, anchor, and path protections. The guarantee therefore belongs to work routed through this harness and its guarded tool surfaces; it is not a claim that operating-system access has disappeared. *[ref: guarded-tool-boundary | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

The preferred path is deliberate: before a phase transition or plugin switch, the agent runs `lock-cmd.sh`. It executes every declared shell test in the plugin. If they pass, it commits the scoped change and clears the lock. If they fail or time out, it refuses to close, preserves both the working tree and the active lock, and shows the failures so the agent can repair them. A plugin with no shell tests can close only with an explicit warning that no verification occurred. *[ref: active-lock-closeout | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

The automatic `safe-lock.sh` path is a defensive backstop for an out-of-scope edit. It runs the same test boundary. On failure, it first attempts a quarantine commit so the work remains recoverable in Git history, then restores the captured checkpoint, preserves ignored plugin state, records failed tests and recovery metadata in the revert log, and clears the lock. Active close-out keeps failed work in place; defensive close-out returns the working tree to safety. The distinction matters because “failure always reverts” would encourage the agent to lose its most useful debugging state during normal work. *[ref: defensive-safe-lock | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

That gate is the foundational pattern in this reference architecture: controls that govern other controls need a protected way to change. Another architect may implement the boundary differently, but removing the contract — named scope, user authority, verification, and recovery — would make the rest of a composing harness harder to trust. *[ref: plugin-integrity-foundational-contract | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

The fuller ceremony — the unlock question, historian ratchet, and plugin-cell anatomy — is deconstructed across two threads. [Essay 5.8](05_8-historian-ratchet.html) shows how several focused plugins compose into the historian ratchet, and the [Essay 7 series](../b7/07_1-plugin-kit-foundation.html) walks the full anatomy of a plugin. What `plugin_integrity` contributes is the admission, scope, test, close-out, and recovery boundary. `question_discipline`, `job_core`, the phase system, and the historian agents contribute the rest through explicit interfaces. *[ref: plugin-integrity-contribution-to-composed-ceremony | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

## Friction calibrated by danger

The lock is a gradient, not a single switch. `[PLUGIN-LOCK]` opens one plugin's protected code surfaces. Inside that plugin, each **existing shell test file** sits behind a second named lock, `[TEST-LOCK]`. The request has its own structured briefing: why this test must change, which groups or fixtures move, and what the suite asserts before and after. A new shell test can be created without unlocking an existing test because addition does not rewrite the established safety net; once the file exists, later edits require the second lock. Editing an existing test therefore carries more ceremony than editing a script, while narrative `CLAUDE.md` work remains outside the plugin lock. *[ref: existing-test-second-lock | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

This is deliberate. The test suite is the safety net under a plugin edit; casually rewriting an established test could weaken the very gate the rest of the plugin trusts. The reference architecture carries large shell-test inventories, but test counts do not establish a coverage percentage and cannot prove that every behavior is protected. The honest rule is more useful: changes to established behavior should bring proportionate regression evidence, and changing existing evidence should cost more attention than adding implementation beneath it. The friction forces the seed agent to state the behavioral delta before it touches the test. *[ref: test-inventory-not-coverage | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

The shape generalizes beyond this reference architecture. **Friction tracks danger.** Reading ordinary project material is cheap. Editing a plugin's code passes through ceremony; editing an established test passes through more — the safety net costs more to lift than the code beneath it. The [gmode](../b6/06_9-gmode.html) lane opens after a long-form `[GMODE]` justification and suspends the ordinary phase restrictions, but it does not erase the plugin lock. This is both ceremony and enforcement: the explanation slows the decision so the operator can judge it, while hooks reject disallowed actions routed through Claude Code's guarded tools. A determined operator with filesystem and Git access remains outside that boundary by design. The design knob this exposes is yours. A lawyer cultivating a brief-template seed could place the heaviest gate over precedent-citation files; a researcher could place it over data-cleaning scripts. You decide which surfaces deserve which gradient. *[ref: friction-tracks-danger-and-trust-boundary | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

## The unlock briefing

At unlock, the agent receives a structured briefing — a header, the plugin's `evolution.md` under a `[LIVING HISTORY]` label, a separate `[RECENT COMMITS]` block listing what has changed since the historian last ran, and three guidance voices: align edits with the plugin's `CLAUDE.md` Objective, `Read` the sibling docs (`docs/decisions.md`, `docs/lessons.md`, `docs/lessons-<topic>.md`) when the LIVING HISTORY references them and the current edit touches that area, and commit before any outside-plugin work. The briefing is bounded but pointed: `evolution.md` is auto-injected (word-capped at 2000); the sibling docs are uncapped and not in the injection path; the second voice tells the agent to follow the references when they apply. The same shape — labeled briefing of accumulated state, plus guidance voices that align edits and point at deeper references — is what other seeds can use at their own decision-rich moments: a consulting seed briefing the agent at the start of every client engagement, a research seed briefing at the start of every literature-review job. *[ref: unlock-briefing-shape | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

## What would break without it

Without a contract like `plugin_integrity`, every plugin edit becomes a hope. Run a change, hope it works, hope you remembered the relevant tests, hope the evidence matches the edit, hope you committed at a recoverable boundary, hope the next session inherits a working codebase. The specific shell machinery is replaceable; the durable value is turning those remembered intentions into an inspectable sequence of scope, authority, verification, and recovery. *[ref: integrity-contract-replaces-remembered-intention | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

Sloppy edits inside one plugin can spread through every plugin that depends on its published surfaces, because plugins compose — they call each other's gateways, share working-memory protocols, and participate in common question and voice registries. A regression in a widely used guard or helper can affect many later actions even when the defect began in one cell. The protected test boundary does not prove the whole harness correct, but it makes each substrate change narrower, recoverable, and harder to pass without local evidence. *[ref: composition-amplifies-regressions | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

## What you would customize

`plugin_integrity` is a plugin most architects should **preserve as a contract even when they reimplement its mechanism**. A protected test-and-recovery boundary is the floor for changing controls that govern other controls. Replacing the shell scripts with CI, a transaction log, a policy engine, or another runtime can improve the architecture; removing named scope, authority, evidence, or recovery makes it less trustworthy. Inside that contract, many knobs remain. *[ref: preserve-contract-not-implementation | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

You would tune the *threshold* — what counts as “verified enough to close.” The reference architecture runs every shell file in the plugin's `tests/` directory with a per-test timeout and treats any failure as red. A plugin with no shell tests closes with a warning instead of pretending it passed. A larger plugin may want fast-and-slow tiers: a focused suite at local close-out and the full matrix in continuous integration. A plugin generating non-deterministic output may need bounded retries or statistical assertions, with the tolerance itself reviewed rather than used to hide flakes. *[ref: plugin-integrity-test-runner | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

You would tune the *question contract* used by the unlock ceremony. In this revision, the shared registry contains ten active prefixes, including plugin locks, test locks, gmode, job approvals, command approval, completion, repeat work, upstream reporting, and waiting. A prefix does not live inside `plugin_integrity` alone: `question_discipline` validates the registered shape, while the owning plugin handles its answer and state transition. Adding a ceremony is therefore a cross-plugin contract change — registry, validation tests, owner handler, and voice must move together. *[ref: prefix-registry-cross-plugin-contract | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

You would extend the *revert log* schema. The current entry already records timestamp, plugin, failed-test context, reverted-file count and paths, the recoverable pre-revert SHA, and whether tests failed or timed out. Your seed might add the test environment, an assertion-level artifact link, the responsible job and cycle, or the later recovery outcome. Richer incident records make CONDENSE faster because it can learn from the actual failure and recovery rather than a generic statement that something went wrong. *[ref: revert-log-schema | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

You would extend the *friction gradient* itself. The reference architecture has a plugin-code stage and a second stage for existing shell tests; it separately forbids direct access to hidden `data.json` state. Your seed may add a reviewed state-schema migration ceremony, a stronger gate for hooks with external side effects, or a separate approval for cross-plugin interface changes. Each added stage is a place where velocity drops on purpose because the consequences rise. The principle stays: ordinary inspection is cheap, dangerous mutation is slower, and the operator chooses the gradient. *[ref: friction-gradient-extension | private historical prototype review | The claim was checked against a private historical prototype; identifying repository, revision, source paths, and unpublished evidence details are omitted from this public record.]*

What you would **not** do is remove the safety net itself. The test gate is the floor; the floor stays.

What This Site Is — and How to Use It

FIVE MINUTES. ZERO SETUP.

A bridge page for newcomers. If you landed here from a search result, a link, or curiosity, this is the right place to start.

The rest of the site uses words such as jobs, plugins, memory, phases, hooks, and harnesses. You do not need to be a programmer to understand what those concepts are for.

What Is a Seed Agent?

A seed agent is an AI assistant whose working system lives in files you control. The language model supplies general reasoning, but the durable structure around it — instructions, memory, jobs, behavioral controls, tools, permissions, and accumulated experience — is the harness.

A mature seed can start from an existing public architecture and grow around your work. A custom harness can also be cultivated from a thinner starting point with you, so you learn its architecture while it is being formed.

It is not simply a chatbot you visit. It is a local workspace whose cognition can become specific to you.

Who Is This For?

Professionals with deep domain expertise and no desire to become software engineers just to own sophisticated AI customization: lawyers, consultants, researchers, project managers, founders, educators, journalists, filmmakers, and others whose work depends on judgment, context, and accumulated knowledge.

The site uses four loose reader layers. Pick the one that fits where you are now; you can move between them as your curiosity changes.

ExplorerCurious. Reads the essays. No commitment.

What you do: Read the blog and form a mental picture of how harnesses work. Nothing to install.

What you read: Part 1 essays (1–4) for the ideas; browse Part 2 if you want the working architecture.

Next: Start with Essay 1.

OperatorUses a seed in daily work. Customizes mainly by talking to it.

What you do: Open a local harness with a CLI agent and describe what to remember, what behavior to change, and what jobs to take on.

What you read: Essays 1–4 for the ideas and Parts 5–8 for enough architecture vocabulary to steer the system precisely.

Next: See the public Codex Seed. It is currently Foundation-stage, so this is the build path rather than a finished installer.

ArchitectDesigns new behavior and understands the underlying compartments.

What you do: Operator work plus architectural decisions: new plugins, memory patterns, jobs, cognitive phases, interfaces, or authority boundaries. Your CLI agent can implement the low-level machinery.

What you read: The full Part 2 series and the implementation/project pages.

Next: Read the technical portfolio or browse the Part 2 series.

ContributorWrites or reviews code, tests, and public harness architecture.

What you do: Architect work plus direct technical contribution to public Seed implementations.

What you read: The repositories, tests, build records, technical essays, and project contracts.

Next: Compare the current implementations and follow the public repositories.

Most people can remain Explorers or Operators. The deeper layers exist because the harness needs to be evolvable, not because every user needs to become an engineer.

What You Are Not Expected to Do

The site talks about plugins, hooks, file hierarchies, state, tests, and architectural patterns. That can sound like “you need to become an AI engineer.” You do not.

You are not expected to

  • Write scripts, schemas, or configuration files by hand.
  • Debug plugin source code as part of normal use.
  • Understand the internals of the underlying language model.
  • Memorize platform-specific implementation syntax.
  • Maintain every low-level mechanism yourself.

You are expected to

  • Talk clearly about your work and judgment.
  • Learn a small architectural vocabulary so you can steer precisely.
  • Tell the agent when a behavior is wrong or incomplete.
  • Understand the important compartments and authority boundaries of your own harness.

The deep material teaches the concepts behind the machinery so you can co-author the architecture with an agent — not so you have to hand-code it.

PowerPoint-Level Vocabulary Is Enough to Start

You need top-level concepts, not syntax. Think of a film director who understands “shot list,” “blocking,” and “wrap” without operating every camera.

Job

A durable unit of work the seed can take on, continue, complete, and report back about.

“Take on a job to draft the standard NDA template.”

Memory

Context the harness keeps because future work may need it.

“Remember that we always report uncertainty separately from the result.”

Plugin

A bounded behavioral or operational capability with a clear objective.

“Add a plugin that checks every report for missing evidence.”

Phase

A compartment for a kind of cognition such as observing, planning, executing, verifying, or consolidating.

“Do not execute yet; return to observation and inspect the new context.”

The vocabulary can become richer as your harness grows, but implementation detail can increasingly be delegated to the CLI agent.

What the Deep Essays Actually Teach

Part 1 (Essays 1–4) introduces the conceptual argument in plain language: why the LLM is not the whole agent, why structure matters, how human cognition is constrained, and what vocabulary lets a person reason about an agent.

Part 2 (Essays 5–8, in mini-series form) documents one real implementation: the now-frozen private Claude Seed. The Always-On Digital Cortex, the OPEVC phasic brain, the Plugin Kit, and the maturation path from soft behavior to harder architecture are concrete examples from that system.

Those essays remain valuable because they show mechanisms that actually coexisted in a working harness. They are reference implementation documentation, not a claim that Codex Seed, Q-Seed, or every client harness must use the same files or exact mechanisms.

If you finish Part 1 you should understand why the harness matters. If you finish Part 2 you should understand one detailed answer to how it can be built.

The Three Things Working Together

Three pieces collaborate every time you use a seed agent. You are one of them.

Conversation

The primary way you shape the harness is by explaining your work, giving corrections, proposing new behavior, and making the decisions that should remain yours.

CLI Runtime

Codex, Qwen Code, OpenCode, or another compatible CLI gives the model tools and access to the local environment. The runtime can change without being the entire identity of the harness.

Filesystem / Harness

Durable instructions, context, memory, jobs, plugins, tests, and other cognition live outside the model session in inspectable assets you can back up, version, and evolve.

You Can Change the Harness in Two Ways

Ownership means there is more than one door into the system.

Through conversation

Tell the agent what should change. A capable CLI agent can inspect the existing harness, propose the right architectural change, implement it, test it, and show you what changed.

This is the default path for non-technical users.

Direct inspection or edit

Open the files, read the state, inspect a rule, review a diff, or edit directly if you want. The architecture should remain legible enough that technical users are never locked out of their own customization layer.

You do not have to use this door, but it should remain available.

The goal is not “no files.” It is that understanding the architecture does not require manually implementing every file.

Two Ways to Start Owning a Harness

Clone a mature public Seed

Start from an existing architecture, learn its terminology and behaviors, then customize cognition and jobs around your work. This is the intended long-term role of the public Seed repositories.

Cultivate one from scratch

For direct individual or team work, start thinner and build behaviors with the user involved from the beginning. Earlier harnesses become pattern libraries rather than code packages to transplant. The learning happens during construction.

Why the Concepts Matter Even If You Never Touch Code

An agent you cannot steer is an agent you cannot meaningfully own. Architectural vocabulary gives you words for the things you should be able to reason about: what is a job, what should be remembered, what behavior deserves a plugin, when a phase should change, what requires verification, and which changes require your approval.

A few hours of vocabulary can buy years of more precise collaboration with a system that keeps evolving around your work.
